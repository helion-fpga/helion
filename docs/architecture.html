Pipeline

Helion is a Rust workspace. Each stage of the flow is a crate with a narrow interface, and the CLI, the Tcl session and the IDE all call the same crates. Device facts live in data files, never in the compiler.

SystemVerilog / VHDL / C
  helion-sv, helion-vhdl, helion-hls      synthesis to the HNF netlist (helion-ir)
  helion-targets                           pick the family backend for the part
    HL10      helion-pack, helion-place, helion-route, helion-bits   -> .hbits
    iCE40     helion-ice40                                           -> IceStorm .asc
    ECP5      helion-ecp5                                            -> Trellis config
    7-series  helion-xilinx7                                         -> FASM, frames, .bit
  helion-sta, helion-drc                   timing, power, CDC, DRC and methodology
  helion-sim, helion-fabric, helion-verif  simulation, testbenches, coverage
  helion-hw, helion-debug                  JTAG, programming, ILA, VIO, JTAG-to-AXI
  helion-proj                              projects, runs, checkpoints, Tcl session
  helion-cli (helion), helion-rune (helion-ide)

The compiler never knows what a LUT is for: the netlist IR is vendor-neutral, and each family implements the Backend trait (pack, place, route, bitstream). Adding a device family means writing a backend, not forking the compiler.

HL10 parts (HAD)

The Helion architecture database (HAD) describes each HL10 part in a TOML file under devices/helion/parts/. CAD code queries these files; it never hardcodes a die. Every CLB has 8 BLEs (a 6-input LUT and a flip-flop each).

HL10T-C32-1 grid: x=0 IO, x=1 clock spine (8 global clocks), x=2..33 CLB, x=34 IO; y=0 IO, y=1..32 interior, y=33 IO. Speed grade 1. There is no HL10 silicon; HL10 bitstreams load into Helion's fabric model and simulator.

Netlist and checkpoints

HNF is Helion's netlist format. Cells, nets and ports carry attributes such as DONT_TOUCH, mark_debug and LOC; (* keep *) and (* mark_debug *) in RTL flow into it. helion hnf file.sv writes a netlist that round-trips. Checkpoints (.hckp) embed the netlist, and restoring one must reproduce the same bitstream hash.

Constraints (XDC/SDC)

Constraint files are parsed by load_xdc in crates/helion-sta. These commands are understood; object queries (get_ports, get_pins, get_clocks, get_cells) appear as their arguments. Unknown commands are ignored.

create_clock               create_generated_clock     set_input_delay
set_output_delay           set_false_path             set_multicycle_path
set_max_delay              set_min_delay              set_clock_groups
set_clock_uncertainty      set_clock_latency          set_disable_timing
set_case_analysis          set_propagated_clock       set_clock_sense
set_input_jitter           set_system_jitter          set_timing_derate
set_bus_skew               group_path                 set_max_time_borrow
set_data_check             set_operating_conditions   set_property

set_property keys: PACKAGE_PIN, IOSTANDARD, DRIVE, SLEW, PULLTYPE, DIFF_TERM, IN_TERM. The Tcl session's flow commands (synth_design, place_design and so on) are a separate list; see the user guide.

Bitstreams

HL10 bitstreams are FeatureMap frames written as sparse .hbits: only configured frames are stored, and partial bitstreams cover DFX regions and ECO updates. The primitives are LUT6, HFF, MAC27 and BRAM18. The vendor-family backends write the formats their open toolchains read: IceStorm .asc, Trellis text config, and FASM with frames and .bit for 7-series.

The IDE

helion-ide is built on Rune, an MIT-licensed Rust UI framework vendored at a fixed upstream commit in third_party/rune. The IDE never reimplements CAD: views read the engine state, and every control goes through the same Tcl verbs the console exposes. Long jobs run on background workers. The UI rule is that a control does real work or renders disabled with the reason.
